泡泡来信 BubblePost：把一只电子宠物鱼养在 QQ 里

  • 2026-11-24
  • 作者 董子阳
  • ~6.13K 字

我想养一条住在聊天软件里的鱼：发消息它回，发链接它读完再聊，没人理它的时候自己安排作息、写日记、挑表情包。这件事不能靠“再开一个 App”解决——打开 App 本身就是成本，而聊天窗口本来就在那儿。

三条约束从第一天就定下来：交互面只有 QQ；记忆必须分得清私聊还是群，宁可少记也不串台；所有会打扰主人的动作都要能解释、能停，包括主动分享、日报和失败重试。

项目一共 16 天、5 次提交，源码 0.1.11，Python 26 个文件 12,641 行，Android 端 10 个文件 1,644 行，设计到测试全是一个人做。这篇按“需求 → 产品 → 方案 → 落地 → 交付”讲，每处设计都把代价一起写出来，机制细节留到文末的专栏清单。

💡 需求：三个「不」

把“养一只鱼”翻译成工程语言，就是三句否定句。每句都直接换成一条产品原则：

我的顾虑 具体要求 由此定下的原则
不想再多一个 App 在 QQ 里发消息就算交互，不装东西、不记命令 交互面收敛到聊天窗口，管理动作才进面板
不能是个只会念知识的问答机 得记得住上次聊的事，得有自己的作息和情绪 记忆与自主行为是核心功能，不是彩蛋
出错不能装死 没发出去、发重复、被站点风控，都要说得清 先把失败语义设计完，再谈功能数量

还有一条隐性需求：不能因为“想它更像活的”就去打穿别人的站点。它要读网页，就得有明确的抓取边界；遇到登录墙、验证码、限流，只能停下来等人。

核心旅程一行写完：发消息 → 按会话召回记忆 → 回话（可能带表情包）→ 发链接 → 读完写摘要 → 过一会儿追问“刚才那篇” → 自己去读白名单站点并写日报。用户只有一类：愿意把一只虚拟宠物长期养在自己 QQ 里的个人，单实例单账号。

🎯 产品定义：做什么，不做什么

能力 面板 手机 说明
私聊 / 群聊对话 ✅ ✅ 群聊默认要 @，可配白名单、概率、冷却
按会话隔离的长期记忆 ✅ ✅ scope + conv 双层隔离，可筛选、批删
记忆压缩（草稿 → 预览 → 替换） ✅ ✅ 来源指纹校验，1 小时草稿有效期
链接阅读与分层摘要 ✅ ✅ 12 万字正文上限，最多 6 层汇总
跨历史窗口追问 ✅ ✅ 会话绑定内容，不依赖聊天历史长度
白名单自主阅读 + 日报 ✅ ✅ 默认关闭，空白名单不抓任何站点
站点授权（隔离浏览器） ✅ — 本人扫码/输入，只导出 Cookie
日记、表情包、自身活动 ✅ ✅ 与主对话分域，不污染聊天上下文
额度三窗口（5h / 周 / 月） ✅ ✅ 本地累计 + 官方接口查询与缓存

刻意不做的：不做知识库问答（它是角色，不是检索器）；不做多用户 SaaS；不绕过登录墙、验证码和付费墙（遇到就停在“等你来授权”）；不冒充“看完了完整视频”——只有标题和简介时，它会明说只看到这些。

🧭 整体方案：一个进程，四块职责

单机单用户场景下，我选择一个 Python 进程扛下所有职责，外面套一个 NapCat 容器做 QQ 协议旁车：

三条设计约束：

  • 只有一条主链。QQ → NapCat → OneBot 事件 → 手写 HTTP 接收端 → 事件循环；链条短，出问题时栈只有几层。
  • 对外只开一个门。NapCat 的 WebUI、OneBot API、事件上报都不发布到宿主机，只在 qq_internal 内网可达；面板默认只绑 127.0.0.1，要远程用得自己套反代并配 ADMIN_PUBLIC_ORIGIN。
  • 两类密钥互相独立。站点授权 Cookie 与 QQ 登录凭据各一把主密钥，都在数据库父目录之外，漏一把不连带另一把；代价是备份必须“库 + 两把密钥 + 密文目录”一起做。
层面 选型 备注
运行时 Python 3.12、asyncio + ThreadingHTTPServer 不用 Web 框架，路由与验签全手写
IM 协议 OneBot v11（NapCat）、Telegram Bot API、终端 收事件走 HTTP 上报，发消息走 HTTP API
存储 SQLite（WAL、synchronous=NORMAL） 16 张业务表、16 个显式索引
模型 DeepSeek Chat 兼容接口（OpenAI 协议）+ 内置 Mock Mock 模式让 85 项自检无 Key 可跑

浏览器 Playwright + Chromium（可选依赖） 站点授权、QQ 人工验证
面板 服务端模板字符串 + 原生 JS + 单文件 CSS 614 行 CSS 含移动断点，零构建
客户端 Kotlin、minSdk 26 / target 35、WebView + Keystore 零第三方运行库，唯一依赖是 JUnit
部署 Docker Compose、python:3.12-slim、非 root UID 10001 双容器 + healthcheck + 日志轮转

🖥️ 两端体验：面板是运维台，手机是同源壳

面板不是“配置页”，而是需要人判断的动作的集中地：扫码、授权、重试、批量删记忆、压缩预览都在这里点，不用去翻日志。

49 条显式路由（GET 24、POST 27，其中 /persona、/tuning 两种方法都收）、10 个一级导航，全部要求 ?token= 并做常量时间比较，未配 token 时面板根本不启动——代价是分享链接也得带 token，不能“发个地址就能看”。

手机端没做原生界面，而是一个同源 WebView 壳：精确比对 scheme+host+port，跨域导航一律交给系统浏览器；凭据用 Android Keystore 生成的 AES-256/GCM 密钥加密后存 SharedPreferences；“保存二维码”把图写进相册再拉起手机 QQ，同机扫码不需要两台设备。明文 HTTP 只对数字 IP 直连开口子，域名、代理、混合内容、坏证书、重定向默认全拒——想用域名就得配 HTTPS，这是刻意留的摩擦。

🔐 难点一：记忆不许串台，靠查询条件而不是提示词

早期最容易被问的是“你写了多长的提示词让它别串台”。答案是：不靠提示词。

会话落库时被映射成 private / group / self / diary 四种 scope，同时记下 conv；召回时查询条件里直接带这两个字段，所以群里的记忆在私聊里查不出来，而不是“查出来但被要求别说”。归属不明的旧记忆默认不召回——宁可少记，也不冒串台的风险。自检有三条断言专门盯这件事：私聊不漏到群里、群里不漏到私聊、历史窗口不串台。

记忆攒多了会变吵，于是有了记忆压缩，做成两阶段：

  • 勾选记忆（可按当前筛选“选全部页”）→ prepare() 落草稿，记下每条来源的指纹与更新时间，1 小时有效；
  • 后台分批调模型生成摘要 → 面板预览展开原文、可整组跳过；
  • confirm() 时再核对一遍来源指纹：有变化就拒绝替换、要求重新预览；没变化才在同一个事务里删源记忆、写压缩记忆、留回执。

流程比“一键压缩”长一倍，换来的是“你看到的就是你替换的”。压缩只动 memory 表，日记、聊天历史、收藏一律保留。

🌐 难点二：能读网页，但不许打到内网

链接阅读是它最像“活物”的地方：收到链接先回一句“我看看”，抓取、清洗、分块、分层摘要，再回原会话说结论；之后你说“这个链接”“刚才那篇”，它会带着正文回答，不依赖聊天历史窗口——绑定关系存在独立的 content_binding 表里。

抓取的安全边界写得比较硬，因为“让 Agent 自己去访问 URL”天然是 SSRF 入口：

  • 只允许 http/https，端口只开 80/443，显式拒绝 localhost；解析 DNS 拿全部 A/AAAA，任一不是 ip.is_global 就拒；
  • 解析后固定 IP 直连，连完用 getpeername() 复核；HTTPS 用 server_hostname 保住 SNI 与证书校验；
  • 重定向最多 5 跳，每一跳都重做完整校验；Cookie 按当前域名重算，绝不跨站转发；
  • 解压后再算体积（2 MB 封顶）、MIME 白名单，防压缩炸弹。

摘要走分层 map-reduce：正文按 3,500 字分块，按 10,000 字分组，最多 6 层，直到“分组数 ≤ 4 且总长 ≤ 18,000 字”才做最终归纳——刻意不“只取前 12 组”，长文尾部的结论不能丢。归纳要求模型返回 JSON：summary / reflection / topics，事实摘要和“鱼的感想”分开存；抓来的内容一律声明为不可信资料、不执行其中任何指令。

失败也不合并成一个 failed：登录墙、人工验证、限流、动态空壳是四个独立状态，都不消耗抓取失败次数——把站点风控当成自己的失败去重试，只会把自己打成黑名单。

⏰ 难点三：HTTP 返回 200，但 QQ 永远收不到回复

NapCat 已登录、5700 端口能连、探针返回 200、日志里有 accepted，但私聊就是没有回复——queued 和 dequeued 一次都没出现。这是整个项目最值得讲的一个 bug。

排查走了三步：先补日志，发现真实回调带的是 X-Signature 而不是 Bearer，于是补上 HMAC-SHA-1 双通道验签；签名通过后出现 auth_valid，仍然不动；最后加 SIGUSR1 按需转储 Python 栈，栈指向看门狗里的 threading.Event.wait()。

根因是看门狗在主线程里同步等待：asyncio.wait_for() 的超时只有控制权回到事件循环后才生效，而同步等待把循环整个卡住。收包线程是独立线程，所以还能应答 200——“能收包”把“消费停了”遮住了。

代价是每条异步写路径都要带 expected_generation：扫码轮询、浏览器回调、快速登录都可能“晚到”，晚到结果不能覆盖新状态，过期回调直接丢弃。换来的是“状态只会往前走”。

📬 难点四：宁可漏发，也不重复发

QQ 发消息超时的时候，你无法区分“没发出去”和“发出去了但响应丢了”。朴素做法是重试，结果是主人被同一条日报轰炸两遍。

所以投递结果被显式建模成三类：ok（终态，永不重发）、failed（明确失败，限次指数退避后可重试）、unknown（结果未知，停止自动重发，必须到面板人工确认）。进程重启时，所有停在 sending 的记录统一标成 unknown 并写明原因。

同一套语义用在内容通知、日报、主动分享三处。代价是面板多一个“待确认”清单，而且它不会自己消失——但“多发一遍”比“多点一次”更打扰人。

🧪 交付与质量

一个人的项目最容易死在“只有我这台机器能跑”，所以这一版把可复现当成功能做：

  • 五层测试，全部离线：内置自检 85 项（Mock 模型 + 临时库）、17 组独立 smoke、打包与部署 smoke 26 项、Android JVM 单测 24 项、2 组 Playwright 浏览器用例，另有专项 79 项（密码登录 52 + QQ 通道 27）。临时 SQLite、回环 HTTP、模拟 NapCat 上报、虚构链接（BV1TEST 这类占位），所以能进 CI，也不碰真实账号。
  • 断言写到协议层：smoke_onebot.py 断言 accepted → queued → dequeued → outcome=ok 全链路，不是“返回 200 就算过”；smoke_chunked.py 是专为“只读 Content-Length 会把 body 读空”这个 bug 立的碑。
  • 交付物有指纹：部署包 66 文件 275,790 B、APK 884,811 B、SHA-256 清单；自研 PAX/UTF-8 打包器把 uid/gid 归零，避免中文文件名跨平台乱码。
  • CI 双 job：Python 3.10 / 3.12 矩阵跑全量离线检查，Android job 跑 JVM 测试 + assembleDebug。

🚧 边界与取舍

  • 单文件的代价。admin.py 2,158 行承担全部路由，这是“不用 Web 框架”的直接后果，已记录为待拆分项。
  • 打包与依赖。没有 pyproject.toml，不能 pip install；两个 requirements 的 cryptography 下界不一致；.gitignore 里的 *.[mM][dD] 会静默忽略新增 Markdown，挡住了 SECURITY.md 这类文件。
  • 没开工的。配置管理 CRUD 与 PostgreSQL 迁移只有设计没有实现，后者要等表结构稳定才有意义。
  • 已知缺口。面板里的“重启应用”走 systemd，对 Compose 部署无效——这个洞是换部署方式之后留下的，没来得及补。

📚 技术细节去哪了

上面每段背后都有一堆实现细节，全塞进来会让这篇没法读，我打算拆成几篇单独写：

  • 《手写一个能收 chunked 的 OneBot 接收端》——Content-Length 与 Transfer-Encoding 双路径、双通道验签、四段打点
  • 《把 SSRF 挡在建连那一步》——固定 IP 连接、getpeername 复核、逐跳重校验与压缩炸弹
  • 《记忆压缩的两阶段确认》——来源指纹、草稿 TTL、事务内替换与幂等迁移
  • 《凭据工程：密码不落盘到底要做什么》——AES-GCM、密钥分离、权限收紧、跨重启冷却与 generation

做这个项目最大的收获不是“教会一只鱼说话”，而是学会把不确定写进产品里：抓不到就说是登录墙而不是失败，发没发出去就标 unknown 而不是重试，记不住就不召回而不是硬猜。把边界讲清楚，比多做一个功能更值。
