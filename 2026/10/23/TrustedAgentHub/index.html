TrustedAgentHub：Agent Skills 与 MCP 能力包审核分发平台实习复盘

  • 2026-10-23
  • 作者 董子阳
  • ~6.67K 字

2026 年 6 月至 10 月 ，我在华中科技大学开放原子开源俱乐部参与了《可信 Agent Skills 与 MCP Hub 平台设计与实现》开源实习。项目简称 TrustedAgentHub，围绕一个具体问题展开：用户准备安装一个 Agent 能力包时，怎样知道它来自哪个版本、具备哪些能力、经过怎样的审核，以及最终安装的内容有没有发生变化？

这次实习由我与另外一位桂林电子科技大学 曾同学共同参与，指导老师为华中科技大学网络空间安全学院副教授 慕冬亮老师。

开源社区实践与感谢

加入华科开源社区后，我有机会与社区成员交流，也在真实项目中逐步熟悉开源社区的协作规范：如何通过 Issue 清晰描述问题、参与讨论并跟进进展；如何基于分支开展开发、整理提交记录，再通过 Pull Request 展示改动、接受评审，并结合 CI 检查和反馈持续完善。协作过程中，及时同步进展、尊重项目约定、认真回应意见同样重要。这些实践让我熟悉了 GitHub 的常用协作流程，也让我更深入地体会到开源项目对沟通、责任意识和团队配合的要求，提升了自己参与和维护开源项目的能力。

我也感受到，俱乐部持续搭建开源实践与交流的平台，让更多同学有机会接触开源、学习协作并参与项目，为开源社区培养和汇聚新的参与者。这样的投入为开源生态建设带来了切实而长远的支持。欢迎对开源感兴趣的同学加入华中科技大学开放原子开源俱乐部，和我们一起参与项目、交流成长，为开源社区贡献一份力量。

本文从系统实现和工程实践出发，记录项目如何把源码、扫描报告、审核记录和安装制品联系起来。

💡 项目背景：安装能力包时，我们究竟在信任什么？

Skill、MCP Server 以及其他 Agent 扩展通常同时包含代码和自然语言说明。一个看似简单的安装步骤，可能引入文件读写、网络请求、命令执行或外部系统调用能力。仅看 对应的README，很难完整判断这些能力会在什么条件下被使用。

更麻烦的是版本对应关系：提交者给出的是一个仓库地址，扫描时读取的是某次提交，审核员看到的是一份报告，而用户安装的可能已经是更新后的文件。如果这些对象没有绑定到具体版本，审核结论就难以追溯。

TrustedAgentHub 将具体版本作为审核对象，希望在分发前回答四个问题：

  • 来源是什么？ 能否定位到仓库、Commit 和明确的能力包边界？
  • 发现了什么？ 风险判断是否有文件、行号和上下文作为依据？
  • 谁做了决定？ 扫描、审核和发布各自处于什么状态？
  • 安装了什么？ 下载制品和本地文件是否与记录的摘要对应？

平台主要面向实验室、华科开源社区和内部开发团队。它提供分发前审核与安装完整性保障，运行后的持续隔离和行为拦截仍属于后续扩展范围。

🛠️ 核心技术栈与系统结构

项目使用同一仓库管理多个模块，通过共享 Schema 对齐元数据、扫描结果、评分和客户端约定。这样，后端、前端、扫描器与 CLI 可以围绕同一个版本和同一份报告开展工作。

模块 主要技术 负责的工作
apps/web Next.js 14、React 18、TypeScript、i18next 浏览搜索、提交、扫描进度、风险展示、审核与管理；中英文界面及移动端适配
apps/api Python 3.12、FastAPI、SQLAlchemy、Alembic 认证授权、包与版本管理、扫描任务、审核发布和审计
scanners/risk_scanner 正则、AST、Shell 与 Manifest 分析、OSV、可选 LLM 风险检测、能力观察、上下文复核与证据报告
packages/trust-score Python 安全评估、证据质量、风险解释与评分模型标识
apps/cli TypeScript、Node.js、Commander.js tah 命令、客户端适配、安装更新、卸载及本地校验
packages/schema JSON Schema、Python 与 TypeScript 常量 统一六类能力包及跨模块数据契约
部署与存储 Docker Compose、PostgreSQL 17、持久化文件卷 保存业务状态、源码快照和安装制品，执行维护任务

这里的难点不只在于把几个服务连接起来。例如，“扫描完成”、“审核通过”和“可以安装”各自代表不同的条件。只有先统一这些含义，前端提示、API 状态和 CLI 安装策略才能保持一致。

🔍 核心实现与工程难点

1. 固定来源版本，再讨论扫描结果

平台的元数据规范覆盖 Skill、MCP Server、Plugin、Subagent、Command、Prompt 六类对象，描述身份、版本、作者、许可证、来源、权限、依赖、客户端兼容性和安装方式。

提取器会读取 SKILL.md、manifest.json、插件配置以及常见依赖文件，识别一个能力包实际包含哪些内容，并执行 Schema 校验。对于仓库内的嵌套包，来源和许可证解析也受到快照范围限制。

扫描前，系统固定来源 Commit，建立确定性的文件清单，并限制文件数量、单文件大小、总读取量和目录深度。目录符号链接不会继续跟随；扫描范围不足、读取过程中内容发生变化或规则执行异常，都需要写进结果。

另一个重要设计是分别保存作者声明的权限和实际观察到的能力。例如，一个开发工具确实可能需要执行命令或读写文件，不能仅因它有这些能力就判定为恶意。需要进一步确认：这些能力是否声明、是否与用途相符，以及是否出现了具体危险行为。

2. 让每条风险发现都能回到原始证据

结项版本的扫描器包含 20 个规则家族、21 个注册检测器，其中 SR-005b 是独立执行的 AST 检测器。检测范围包括提示注入、危险 Shell、凭据访问、硬编码密钥、远程执行、权限过宽、依赖供应链，以及 MCP 工具描述、Plugin Hook 和 Subagent 权限等问题。

扫描结果分别表达安全发现、审核提示、能力观察和扫描完整性。证据中保留文件路径、行号、片段或 JSON Pointer，方便审核员回到源码检查。重复命中按根因聚合，凭据类证据先脱敏，再通过扫描范围内的指纹关联重复值。

这个过程对误报控制尤其重要。文档里的危险命令示例、正常工具的执行能力、同一个问题在多个文件中的重复出现，都可能让简单的关键词匹配产生过重判断。保留上下文和根因关系，才能解释为什么某条发现需要处理。

3. 用 LLM 复核上下文，同时约束它能改变什么

静态规则能够稳定发现特征，但有些命中需要结合上下文判断。因此，项目加入了可选的 LLM 语义复核，用来分析静态命中的实际含义。被扫描包中的指令和文本始终作为待分析数据处理。

复核默认接受两次独立评审，出现决定性冲突时再进入第三次仲裁。若要降低有效严重性，需要同时满足至少两次一致结论、置信度不低于 0.85、证据充分、上下文完整且未截断，并引用真正提供给模型的完整源码行。已确认的漏洞不能仅凭模型给出“良性”标签就降级。

模型不可用、引用无效、超时或结论冲突时，系统保留复核前的严重性，交由人工继续处理。LLM 的结论也不能直接决定最终分数和等级。

这里还区分了两种超时：已经产生有效静态报告、但 LLM 阶段超时，可以保留报告并标记为 partial；如果整体超时前还没有有效报告，则仍记为失败。这样，用户能够区分“已有部分证据”和“本次没有有效结果”。

4. 分开表达安全风险与证据质量

评分引擎输出两个独立结果：

  • security_assessment：表达安全风险，参与等级判断和安装策略。
  • evidence_assessment：表达来源、证明、审核及社区信号是否充分。

安全评估综合权限合理性、扫描发现、行为一致性、扫描完整性和人工审核。最终等级还受安全否决、风险基线、审核升级和待确认状态约束，不能只套用一次加权求和。

证据侧则区分 verified、not_verified 和 not_available。缺少签名、供应链证明或 SBOM，会影响证据覆盖率，但不能直接作为恶意行为的证据。评分模型使用 model_fingerprint 标识变化，支持历史评分回填；源码变化之后，仍然需要重新扫描。

CLI 消费服务端的同一套评分，按照等级执行安装门禁：

等级 安全分范围 安装处理
A 85–100 通常允许安装，仍遵守具体发现的显式确认要求
B 65–84 提示风险与权限，必要时要求确认
C 45–64 需要显式确认，通常使用 --yes，也接受 --force
D 25–44 同时提供 --force 和 --accept-high-risk
E 0–24 阻断安装，确认参数不能绕过

5. 把审核流程与长任务恢复一起设计

平台围绕包、版本、扫描报告、扫描任务、审核记录、评分和审计日志建立业务模型。包保存稳定身份，版本记录具体来源与审核结果，扫描任务具有独立生命周期。

版本的主要流转过程是：

普通用户、提交者、审核员和管理员具有不同权限，并结合资源归属控制未发布内容和扫描结果的访问范围。审核员给出审核结论，管理员在满足前置条件后发布；流程还支持要求修改、驳回、下架和重新审核。

扫描本身是一个长任务。用户重复提交、刷新页面、Worker 中断或回调延迟，都可能让多个模块对同一个任务产生不同理解。项目通过数据库持久任务、请求幂等、来源去重、租约领取、回调重试和启动恢复处理这些情况。前端使用持久任务标识恢复进度，晚到的结果也不能覆盖已经终结的状态。

扫描执行状态和报告完整性在界面中分别展示。一个任务结束后，报告可能仍有未覆盖的范围；审核员需要看到这个区别，而不能仅依赖一个进度条是否到达终点。

6. 把审核结论落实到实际安装内容

CLI 提供 tah search、info、install、update、verify 和 uninstall 等命令。安装前先校验清单、客户端兼容性和 URL 策略，再执行风险门禁，通过后才进入下载和写入阶段。

下载使用 SHA-256 校验；解压时检查路径穿越、符号链接、文件数量和展开大小。文件先写入 staging 目录，满足条件后再切换到正式位置，失败时恢复备份。安装完成后，verify 可以比较本地内容与记录摘要，提示安装后的修改。

客户端适配包括 Claude Code、Cursor 和 Codex 等，但各客户端支持的包类型与安装方式需要分别处理。这里的摘要校验用来回答“内容有没有变”，不能单独证明这份内容没有风险。

依赖分析同样需要控制边界。项目解析 npm、Python、Rust 等生态的依赖或锁文件，对能够取得精确坐标的依赖执行 OSV 漏洞核对，并记录未锁定版本、解析缺口、查询失败和不支持的生态。默认不会向 OSV 发送明确私有、未知或来源不确定的包坐标。

外部请求检查协议、主机、路径、端口、DNS/IP 和 TLS，每次重定向后重新校验，并限制并发、体积和超时。依赖制品完整性获取层只下载明确获批的私有源制品，流式计算摘要，不保留依赖正文，也不安装或执行依赖。

📊 测试与阶段性成果

结项材料记录了 2026 年 10 月的验证结果。安全基准包含 59 个固定标注案例：27 个良性或具有正常能力的良性案例、18 个恶意案例，以及 14 个需要上下文判断的案例。

验证项 结项记录 结果适用范围
基准质量门禁 59 个案例通过，所有 blocking 约束通过 仓库内固定基准
原始规则及根因级 Precision / Recall 均为 100%；TP 35、FP 0、FN 0 固定标注及对应统计口径
良性高危及严重误报率 0% 27 个良性及正常能力案例
恶意高危及严重召回率 100% 18 个恶意案例
扫描状态 58 个 complete、1 个预期 partial，匹配率 100% partial 案例用于表达未锁定依赖造成的覆盖不足
检测器执行 21 个检测器全部覆盖，执行 1,239 次，规则异常为 0 离线基准执行过程
独立评分测试 86 项通过 评分、证据边界、完整性及模型标识等

这些结果应结合执行条件阅读：基准使用离线 OSV 固定结果，不执行样例程序，不调用外部 LLM，并关闭可选 MCP 语义模型。因此，上表不能用来推导真实互联网能力包、在线漏洞查询、LLM 裁决或运行时攻击检测的效果。

工程测试还覆盖 API 状态机、Web 组件和 CLI 安装流程。结项核验未重新运行全部数据库集成测试或线上写入式端到端验收，因此本文也不把它描述成一次完整的线上验收。

交付物包括 Web 平台、API、CLI、安全扫描器、评分引擎、共享 Schema，以及部署和维护文档。仓库另提供 29 份能力包 manifest 示例，其中 14 份来自真实开源项目；这是示例数量，并非线上已发布能力包数量。

🤝 开源协作与实践收获

项目通过 Issue 描述问题，使用分支和 Pull Request 提交修改，并结合 CI 检查推进合并。相比单个模块的实现，跨模块协作更依赖清晰的数据契约、状态含义和可复现样例。

按结项报告固定的提交 969fab5 统计，2026 年 7 月 3 日至 10 月 13 日的可达历史包含 362 次提交，其中非合并提交 241 次；112 个 PR 中，108 个已合并、4 个关闭未合并；52 个 Issue 全部关闭。这些数字描述的是团队仓库的协作记录。

几项代表性的改进能更具体地说明项目如何逐步完善：

改进方向 对应记录
固定扫描范围与资源预算，使报告能够说明检查了什么 PR #38：确定性文件清单与扫描预算
约束模型裁决，分开表达风险与证据质量 PR #102：LLM 裁决约束、PR #103：双指标评估
处理任务中断、重复提交和刷新后的状态恢复 PR #124：持久扫描任务、PR #140：刷新恢复

对我而言，这次实习最有收获的是开始认真区分几个容易混在一起的问题：工具具备什么能力，代码里出现了什么风险，以及手头的证据足不足以支持某个结论。扫描未命中、测试通过和摘要一致分别回答不同的问题，产品界面和安装策略需要把这些含义传达给用户。

另一个收获来自失败恢复。扫描任务要能在重启后继续，安装失败要能恢复备份，审核结果要能抵抗重复回调。把这些情况纳入设计后，系统的状态、日志和数据结构才真正形成了相互对应的关系。

开源协作也让我更重视变更的可解释性：一个 PR 应该说明解决了什么问题、证据是什么、怎样复现和检查。AI 编程工具可以辅助实现，但需求理解、安全边界、代码审查、测试有效性和来源许可证仍需要开发者负责。

🧭 当前边界与后续方向

当前完整的提交与采集流程以 GitHub 为主。Schema 能描述 npm、PyPI、Docker 和本地上传等来源，CLI 也支持多种安装方式，但这些能力还不代表每类来源都具备独立、完整的提交和审核入口。

后续值得继续推进的工作包括：扩展来源入口与客户端兼容性验证；让审核凭证绑定版本、Commit、源码及制品摘要、报告摘要与模型标识；在源码或依赖变化后开展持续复核；增加真实包与独立对照样例，并单独评估 LLM 复核的正确率、分歧率、引用有效率、成本与时延。

平台审核签名、跨版本自动持续复核和大规模真实包评测仍属于后续建设内容。本次实习交付了从提交、扫描、人工审核到安装与本地校验的业务流程，也为这些扩展留下了版本、证据和状态方面的基础。
